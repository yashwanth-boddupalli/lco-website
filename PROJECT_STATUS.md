### Database objects created (`complaints_setup.sql`)

Table `public.complaints`:

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID PK | `gen_random_uuid()` |
| `complaint_id` | TEXT UNIQUE | Generated by the database: `CMP-0001`, `CMP-0002`, … |
| `customer_id` | UUID | FK → `public.customers(id)`, resolved server-side |
| `created_by` | UUID NOT NULL | FK → `public.profiles(id)`, defaults to `auth.uid()`; ownership anchor for RLS |
| `category` | TEXT | CHECK: Internet Not Working, Slow Internet, Cable TV Not Working, Signal Issue, Installation Issue, Payment Issue, Other |
| `description` | TEXT NOT NULL | Non-empty |
| `priority` | TEXT | CHECK: low, medium, high, urgent (default `medium`) |
| `status` | TEXT | CHECK: pending, assigned, in_progress, resolved, closed (default `pending`) |
| `technician_id` | UUID NULL | FK → `public.profiles(id)`; placeholder for the future Technician module |
| `created_at` / `updated_at` / `resolved_at` | TIMESTAMPTZ | maintained by triggers |

Functions / sequences / triggers:

- `public.complaint_id_seq` — sequence backing the readable ID
- `public.generate_complaint_id()` — returns `CMP-####` from the sequence
- `public.tiranga_is_admin()` — SECURITY DEFINER admin check (used by RLS)
- `public.tiranga_resolve_customer_id(uuid)` — SECURITY DEFINER map of an auth
  user to their `customers` row; returns NULL when `customers` has no auth link
  column
- `public.handle_new_complaint()` + trigger `on_complaint_created` — assigns the
  complaint ID, forces `created_by = auth.uid()`, resolves `customer_id`, forces
  `status = 'pending'` and the timestamps
- `public.handle_complaint_update()` + trigger `on_complaint_updated` — freezes
  identity columns, refreshes `updated_at`, sets/clears `resolved_at`
- Indexes on `created_by`, `customer_id`, `status`, `priority`, `created_at`

### RLS policies created

RLS is enabled on `public.complaints`.

| Policy | Command | Rule |
|--------|---------|------|
| Customers can create own complaints | INSERT | `WITH CHECK (created_by = auth.uid())` |
| Customers can view own complaints | SELECT | `USING (created_by = auth.uid())` |
| Admins can view all complaints | SELECT | `USING (public.tiranga_is_admin())` |
| Admins can update all complaints | UPDATE | `USING/WITH CHECK (public.tiranga_is_admin())` |

No policy reads `complaints` from inside a `complaints` policy, and the admin
check runs inside a SECURITY DEFINER function, so the infinite-recursion problem
previously hit on `profiles` cannot occur here. No DELETE policy exists —
complaints are never deleted in Phase B.

### Verification performed

- `complaints_setup.sql` was executed against a throwaway PostgreSQL 16 instance
  with a stub `auth` schema, `profiles` and `customers`, covering:
  sequential `CMP-0001`/`CMP-0002` generation, forged `complaint_id` /
  `created_by` / `status` being overwritten, customer isolation (a second
  customer sees 0 rows and cannot update), admin visibility and updates,
  `resolved_at` / `updated_at` bookkeeping, the customer seeing the admin's new
  status, re-running the migration (idempotent), and the fallback path when
  `customers` has no auth link column.
- `js/complaints.js` passes a Node syntax check.

### Not yet verified (blocked)

The end-to-end browser flow (customer login → submit → Supabase → admin →
status change → customer sees update) has **not** been run against the live
Supabase project: it requires `complaints_setup.sql` to be executed in the
Supabase SQL editor plus a test customer and admin login. Until that is done,
Phase B should be treated as implemented but untested in production.

### Features not implemented (out of scope for Phase B)

- Technician portal / technician table. `technician_id` is nullable and the
  assignment dropdown is populated from `profiles` where `role = 'technician'`;
  when a dedicated technician table lands, only
  `TirangaComplaints.getTechnicians()` and the `complaints_technician_id_fkey`
  constraint need to change.
- Billing, payments, notifications, AI, analytics.
- Complaint comments/history timeline, attachments, SLA tracking.

### Known issues / notes

- **Multi-LCO scoping**: the schema has no `lco_id`, so an admin sees every
  complaint in the database (single-LCO deployment). Add an `lco_id` predicate to
  the two admin policies when multi-LCO support arrives.
- **Customer ↔ auth link**: `customer_id` is filled only when `public.customers`
  has a column linking to auth users (`user_id`, `profile_id`, `auth_user_id` or
  `auth_id`). If it has none, complaints are still stored and owned correctly and
  the admin UI falls back to the reporter's profile name/phone, but the Area
  column shows `—`. Adding such a column to `customers` is the fix.
- The existing `profiles` admin policies still query `profiles` from within a
  `profiles` policy (see `profiles_setup.sql`). That is pre-existing and was not
  changed in this phase; `public.tiranga_is_admin()` is available if you want to
  rewrite them safely later.

### Technician ID generation

`public.technician_id_seq` + `public.generate_technician_id()` (SECURITY
DEFINER, `search_path = public, pg_temp`) produce `TRG-TECH-####` from a
sequence, so concurrent inserts cannot collide. `EXECUTE` is revoked from
`PUBLIC` and granted only to `authenticated`, so anonymous callers cannot burn
identifiers through PostgREST RPC.

### Security model / RLS

RLS is enabled on `public.technicians`.

| Policy | Command | Rule |
|--------|---------|------|
| Technicians can view own record | SELECT | `profile_id = auth.uid()` |
| Admins can view all technicians | SELECT | admin helper |
| Admins can insert technicians | INSERT | admin helper |
| Admins can update technicians | UPDATE | admin helper |
| Admins can delete technicians | DELETE | admin helper |

No policy reads `technicians` from inside a `technicians` policy, and the admin
check is a SECURITY DEFINER function rather than an inline `profiles`
sub-select, so the recursion problem previously hit on `profiles` cannot occur.

### Indexes

`profile_id`, `technician_id`, `area`, `status`, `phone` — all created with
`IF NOT EXISTS`.

### Verification performed

Run against a throwaway PostgreSQL 16 with a stub `auth` schema and `profiles`:
migration applies cleanly and is idempotent on re-run; `TRG-TECH-0001` /
`TRG-TECH-0002` generated in order; the `updated_at` trigger fires only on the
updated row; a technician sees exactly their own record and cannot update,
delete or insert; and on a database *without* `is_admin()` the migration creates
it and still installs all five policies.

No SQL was executed against the live Supabase project — the migration must be
run manually in the SQL editor.
